# #24A — Current interface audit

Scope: [Issue #24](https://github.com/ProBatou/DebBuilder/issues/24) and its Zoraxy, Pocket-ID, and #30 comments; code at `4958a5bc4f601aaf31de2b52cb69665abc2b325e`. This is an audit of the shipped GitHub-only product, not a specification for #25. Findings below distinguish **visual debt (V)**, **UX/workflow debt (U)**, and **architecture debt (A)**. See [information architecture](information-architecture.md), [progressive disclosure](progressive-disclosure.md), [frontend decision](frontend-architecture.md), [visual directions](visual-directions.md), and [migration plan](migration-plan.md).

## Evidence and scope

- Read `static/index.html`, `static/style.css`, `static/css/{components,pages}.css`, every `static/*.js`, `static/js/{pages,recipe}/*.js`, Recipe v5 schema and packaging paths, and `debbuilder/repository_templates/index.html`.
- Ran the isolated `tests.ui.behavior_lab` at a local port and used Playwright Chromium at 1440×1000 and 390×844. Inspected Dashboard, Packages, Recipes, Runs/Logs, System, and Settings in `showcase`, then Run detail in `cancellation-running`, `queued-cancellable`, `build-failure`, `prepared-test`, `graceful-shutdown`, `recovery`, and `recovery-blocked`. Some short-lived running/failure fixtures finished before first selection; their static/recovery counterparts and code were used for terminal-state review. Screenshots were temporary under `/tmp`, not design references.
- The admin frontend has 16 JS files (about 4,558 lines), 3 CSS files (about 1,445 lines), and a 387-line HTML document. About 240 named functions are spread across global scripts. `app.js` is 628 lines; `logs.js` 584; `packages.js` 492; `settings.js` 381; `recipe_serialization.js` 352. The largest responsibilities are `renderSettingsPage`, `renderOpenExecution`, `renderOpenPackage`, `collectWorkflow`, and `renderWorkflow`; size alone is not the defect, but each mixes data translation, state and markup.

## Code and behavior map

- `index.html` contains all six view roots and dialogs. Classic ordered scripts share globals. `js/admin.js` owns `adminState`, routing, mobile nav, action dispatch and initial wiring. `app.js` owns Recipe selection, applicability, autosave and Test/Build submission. `recipe_serialization.js` translates Recipe v5 to/from DOM; `json_editor.js` separately validates/imports/applies JSON. `settings.js` holds dirty/revision/save timers and renders Settings. `ui_core.js` provides escaping, status labels, fetch helpers, dialogs and preflight primitives; `build_insight.js` renders preflight.
- `pages/{dashboard,packages,logs,system}.js` own page requests and markup. `recipe/{archive_tree,automation,source_changes,stepper,test_run_modal}.js` add specialized state. The current split is useful but depends on script load order and mutable global variables. `pages.css` contains most page styling; `components.css` has partial shared primitives; `style.css` includes tokens, reset and shell. Repeated button/badge/card conventions and overlapping page selectors complicate global visual changes.
- Polling is explicitly scoped: Test modal, open live Run/log, Package validation and Recipe automation each schedule/cancel their own timeout; navigation stops relevant timers. Cancellation, `409 execution_not_cancellable`, submission-in-flight, settings/Recipe autosave revisions, log offset/follow mode, and package validation attempt IDs are important hidden behavior.
- API calls use common `getJson`/`postJson` in some places and direct `fetch` in others. Source archive inspection, Run submission, Recipe CRUD/validation/import, package and automation actions, logs, validation, publication, settings/storage, diagnostics/inspectors/support bundle are distinct contracts. Structured errors should survive a presentation refactor.

## Accessibility and responsive findings

Visible strengths: native labels wrap many inputs; most dialogs use `<dialog>`; focus and status tokens exist; status text accompanies color in most badges; responsive CSS exists at 900/600px; mobile Run list/detail back flow exists. Obvious checks before migration: hamburger button needs a stable accessible name; package drawer needs dialog semantics, focus trap/return and Escape close; `role=listbox` Run rows must support arrow-key selection or use simpler list/buttons; several rendered clickable `<div>` rows rely on delegated keyboard handlers and need systematic coverage; dialog focus return after asynchronous close; contrast of tiny muted text and disabled actions; status changes must be announced selectively (avoid noisy live log); reduced motion currently depends mostly on minimal animation, so add explicit policy for future transitions; 32/38px controls and tiny row actions need touch target review; mobile Recipe step names must stay available to screen readers and preferably visible.
